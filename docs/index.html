isère

Serverless functions on a microcontroller

isère is a platform for running serverless functions on microcontrollers, such as the Raspberry Pi Pico 2. You write a function in JavaScript; isère routes requests to it, runs it, keeps it from hurting its neighbours, and tells you what every call cost. This is the story of making it do real work, fast.

Every number on this page comes from the Linux build of isère (FreeRTOS's POSIX port, in Docker on an Apple-silicon Mac), not from the Pico 2 itself. The same code, tests and benchmark script run on the board; its numbers will be published when the hardware loop has run. The raw figures are in BENCHMARK.md.

What isère is

Serverless platforms let you deploy a function and forget about servers. isère brings that model to a microcontroller: a board on your desk, or a $5 chip in a device, serving functions over HTTP.

  • A function is a JavaScript module in the Cloudflare Workers style, so the same code runs on isère, on Workers, or in Node. QuickJS and JerryScript both run it.
  • Many functions per board, each routed by method and path. Static files are served without touching JavaScript at all.
  • Functions don't hurt each other. One that throws, hangs, loops forever, recurses without end or runs the engine out of memory fails that one call with a 5xx.
  • The platform APIs functions expect: Request, Response, Headers, URL, fetch over HTTP and HTTPS, crypto.subtle, timers, and configuration through env.
  • Every call is measured: wall time, CPU time, bytes allocated, peak heap and the heap it left behind, in a Server-Timing header and at /__metrics.
// a function: a module in app/, routed in app/routes.json
export default {
  async fetch(request, env) {
    return new Response('hello from isère\n')
  },
}

A first real use case: verifying JWTs

A platform claim needs a real workload behind it. Not "blink an LED over HTTP", but a function people would actually deploy, with crypto, caching, an outbound network call and a budget. The first one we picked is something every API gateway does:

  • GET /verify reads Authorization: Bearer <jwt>, finds the key by kid in a JWKS cached in memory, verifies the RS256 or ES256 signature, and answers 200 with the claims or 401.
  • GET /.well-known/jwks.json publishes the board's own keys. The verifier can fetch its JWKS from the board it runs on, which makes a self-contained benchmark fixture.

The whole verifier is an ordinary isère function. Its JWKS cache is a module-level variable, which works because isère keeps each function's module alive between calls:

// app/verify.js, shortened
import { JwksCache, verify } from './jwt.js'

let cache = null   // lives as long as the engine: one JWKS fetch per TTL

export default {
  async fetch(request, env) {
    if (cache === null) cache = new JwksCache({ url: env.jwks_url, ttlMs: env.jwks_ttl_ms })
    const m = /^Bearer (\S+)$/.exec(request.headers.get('authorization') || '')
    if (!m) return Response.json({ error: 'missing bearer token' }, { status: 401 })
    return Response.json({ claims: await verify(m[1], cache) })
  },
}

Where it started

isère already ran JavaScript functions on the Pico 2 before this work began, and it was honest about being a prototype. Its request path looked like this:

  • One function per board, evaluated from source on every request, in a brand-new engine runtime per connection. There was no routing and no state between calls, so a function couldn't even keep a cache.
  • Fixed-size fields. Header values were truncated at 63 characters (a real JWT is several hundred), and about 10 KB was reserved per connection whatever the request.
  • Every request copied three times, in 64-byte reads, with strdup on the way out. A response body containing a NUL byte leaked adjacent heap memory to the client.
  • JS timers ran on FreeRTOS's timer task, a second thread touching the same engine as the HTTP task.
  • No outbound HTTP, no TLS, no crypto: fetch was a stub.
  • JerryScript hung after about 29,000 requests under wrk, and QuickJS leaked on cleanup.

Measured then, on different hardware and with wrk's connection-per-request load, QuickJS served about 300 requests per second and JerryScript about 3,700. On the Pico 2, 12 and 41.

What changed, and why

Warm engines: the single biggest win

Each function's module is now evaluated once, at boot, and every request is a fresh function call into it. A request on QuickJS costs about 10 µs of engine work instead of building a runtime, a context, the polyfills and the module from scratch.

A runtime per request is the wrong default for a server. It looks like isolation, but the isolation that matters is that one function can't hurt another, and you get that from deadlines, interrupts and per-request cleanup, not from rebuilding the world. A busy loop, an endless await, unbounded recursion or an engine out of memory now fails that one request with a 5xx; the next request doesn't notice. The old mode is still there behind ISERE_JS_MODE=cold, because a test that creates and frees an engine on every request is the best way to prove cleanup is correct.

One event loop, one task

Everything isère does runs on one FreeRTOS task, around one poll(): sockets, HTTP, JS timers, fetch, both engines. FreeRTOS is reduced to what it's good at: scheduling isère next to the USB and network stacks on the board. Nothing needs a lock, and the timer race disappeared with the timer task's role.

Parse in place

The HTTP parser follows picohttpparser: every recv re-parses the head from the start of the connection's own buffer and records each field as an offset and a length into it. Nothing is copied until the request crosses into the JS engine, once, with length-aware calls. There are no per-field limits, only a budget for the head and one for the body.

Offsets, not pointers, is the whole trick: the buffer can grow by realloc between reads and every field stays valid. And strict beats lenient: obsolete line folding, control characters, duplicate Content-Length, or Content-Length with Transfer-Encoding all get a 400, because every one of them is a request-smuggling vector in some proxy. The parser runs under libFuzzer and AddressSanitizer in CI.

One API, both engines

isère keeps both QuickJS and JerryScript. Instead of writing every API twice, one JavaScript prelude builds Request, Response, Headers, URL, fetch, crypto.subtle and timers for both; each engine binding only supplies a dozen natives. fetch speaks HTTP and HTTPS over the same event loop through mbedTLS, and can even call the server it runs on, with reserved connection slots so a full pool can't deadlock it.

Measure, then believe

Every response carries a Server-Timing header with what that request cost. The CPU time counts only the stretches where the request's own code ran, not the time it spent waiting on the network or a timer. Calibration endpoints with known costs keep the numbers honest:

Calibration endpointExpectedReported (both engines)
/__calibrate/cpu5 ms of CPUwithin ±10%
/__calibrate/alloc32 KB allocated and freedwithin ±10%
/__calibrate/sleep100 ms of wall time, no CPUwithin ±10%, CPU near zero

A metric you haven't calibrated is a guess with decimals. The calibration tests caught our own first mistake: JerryScript's large buffers were allocated outside its heap, so it reported 24 bytes for a 32 KB allocation.

The numbers

Each engine ran for ten minutes: four scenarios at 1, 2 and 4 keep-alive connections (4 is the Pico 2's connection limit), 50 seconds each, with a fresh server per cell. Not one request failed, and after garbage collection no cell kept a byte per request.

QuickJS wins every JavaScript scenario, about twice as fast as JerryScript on both the trivial function and on JWT verification. That's a reversal: before the warm engines, JerryScript was twelve times faster, because QuickJS paid for a whole runtime on every request and JerryScript's was cheaper to build. Compare engines on their steady state, not on how fast they can be thrown away.

On a cold request, parsing the prelude dominates. Two fixes help when you must run cold: compiling only the parts of the prelude a handler touches (URL, fetch and crypto load lazily) cuts it by about 35–40%, and loading QuickJS bytecode instead of source nearly removes it. A warm engine removes it entirely.

Things that surprised us

Most of the speed didn't come from clever code. It came from finding costs nobody had looked at.

What we foundWhat it cost
FreeRTOS's heap_3 wraps every malloc in a critical section; in the POSIX port that's two signal-mask syscalls per allocation.Half of QuickJS's throughput. Calling malloc directly took GET / from 82k to 127k req/s, and JWT verification from 3.7k to 8.0k.
A closed connection left a dead slot in the poll set; libuv purges them, our copy of its code had lost the line.Every connection ever served made poll() a little slower and the heap 13 bytes bigger. Fixed, connection-per-request throughput went from 9.3k to 26–28k req/s.
mbedTLS and JerryScript were compiled without optimisation, because nothing set a build type.RSA verification several times slower than it should be.
atob() in JavaScript, with an indexOf per character.Most of a JWT verification. In C, it cut verification from 246 to 151 µs on QuickJS and from 717 to 294 µs on JerryScript.
Reading the per-thread CPU clock is a system call on Linux.8% of throughput for metrics alone. A stretch of request work never blocks, so the monotonic clock measures the same thing for 20 ns; calibration still holds.
FreeRTOS defaults to 16-bit ticks.Nothing yet: the tick counter would wrap every 65 seconds at 1 kHz. Found while documenting every setting.
Running out of heap is fatal to JerryScript: it calls exit().A handler that allocated too much took the server down. Now the fatal handler jumps back to the binding, which throws the engine instance away and starts a fresh one; the request gets a 500.
JerryScript measures stack use from where the engine was created, not where it is called from.Callbacks from shallower frames looked like stack overflows. A small helper now moves the base on every entry.

QuickJS or JerryScript?

Both, for now, and the reasons pull in different directions.

QuickJS (quickjs-ng)JerryScript
Throughputabout twice JerryScript's
Languagemodern; parses everything we wrotea few gaps, e.g. export async function
Memorygrows on the shared heap, bounded by the budgetone fixed arena: predictable, and its exhaustion is contained
Stack at boot (64-bit)21 KB6 KB
Stack verifying a JWT over HTTPS36 KB10 KB

On Linux, QuickJS is the obvious choice. On the board, the deciding number may be the stack, not the speed: the Pico 2 gives the HTTP task 24 KB, and QuickJS uses 21 KB just to boot on a 64-bit host. If that holds on the 32-bit board, JerryScript's fixed arena and small stack are worth more there than a factor of two in throughput. The hardware loop will settle it.

What's next

  • The board. Run the same suite and benchmark on a Pico 2 through the hardware loop, and size its stacks and heap from what /__metrics reports.
  • The outside world. Route the board's traffic through the USB host, for HTTPS JWKS and OpenTelemetry, and give it wall-clock time, so JWT expiry means something there.
  • More use cases. JWT verification is the first workload, not the last; each new one should bring its own tests and benchmark scenario.
  • The platform question. A Zephyr/Rust build exists as a spike. It will face the same tests and benchmark before anyone chooses a stack, and whichever wins has to own its event loop and HTTP parsing.
